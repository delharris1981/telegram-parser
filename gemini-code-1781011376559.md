# Project Specification: TeleListener-RU (Telegram Keyword Listener & Dashboard)

## 1. Objective & Scope
Build a localized, robust, future-proof Telegram Keyword Parser ("UserBot") and companion Web Dashboard. The system will monitor specified public Russian Telegram open chats for exact-keyword matches, capture the user's profile info and the original comment, store the hits in a local database, and display them on a clean, password-protected web interface. 

Additionally, the system will feature a configurable notification loop that can dispatch live alerts with direct clickable links back to the source profile straight to a specified Telegram handle, group, or account.

### Core Architectural Separation
To ensure long-term maintenance and future-proofing, the codebase MUST be modular and cleanly split into distinct components linked via a shared database:
1. **Core Parser Component:** A continuous background script handling Telegram connections.
2. **Database Component:** The centralized, isolated storage layer.
3. **Web Dashboard Component:** A lightweight front-end and web API.

---

## 2. Environment & Infrastructure Requirements
* **Hosting Target:** Beget.com Cloud VPS (Virtual Private Server) running Ubuntu Linux.
* **Runtime Environment:** Python 3.10+ using Asynchronous Programming (`asyncio`).
* **Database:** SQLite configured explicitly in **Write-Ahead Logging (WAL)** mode (`PRAGMA journal_mode=WAL;`) with an aggressive connection timeout (`timeout=10.0`) to natively prevent multi-process database locks between the background writer and web reader.
* **Web Framework:** FastAPI or Flask (FastAPI preferred for async performance).

---

## 3. Component Specification & Implementation Guidelines

### Component A: Python Telegram Parser (Background Worker)
* **Library:** Use `Telethon` or `Pyrogram` (Client API) via your own Telegram API ID and Hash (UserBot configuration) to allow "lurking" and parsing inside public groups. Do *not* use standard BotFather API tokens.
* **Auto-Join Logic:** * Implement an auto-join feature for public groups via invite links or public handles.
    * **Strict Anti-Flood Measures:** Integrate an exponential backoff algorithm and a mandatory randomized delay (60 to 300 seconds) between channel joins to prevent `FLOOD_WAIT` bans from Telegram.
* **Localization (Russian-Only Gatekeeper):**
    * *Group Filtration:* Automatically check group titles and descriptions for Cyrillic characters (`[а-яёА-ЯЁ]`) during search or discovery phases before attempting to join.
    * *Message Filtration:* Apply a fast regex-based gatekeeper at the start of the message event handler. If a message contains zero Cyrillic characters, skip processing immediately to preserve CPU.
* **Keyword Detection:** Execute an exact-string case-insensitive match on the clean message text against the user-defined keyword array.
* **Spam Layer:** Ignore any messages where the sender account is verified as a bot (`message.sender.bot == True`). Ignore messages containing structural spam patterns like raw broadcast referral links (`t.me/joinchat/` or `t.me/+`).

### Component B: Database Schema (SQLite)
Create a clean relational schema inside a single `telelistener.db` file tracking:
* `keywords`: (id, phrase, created_at)
* `monitored_groups`: (id, telegram_id, title, handle, joined_at)
* `parsed_hits`: (id, group_id, sender_id, username, first_name, original_comment, keyword_matched, captured_at)
* `settings`: (id, tg_notifications_enabled, tg_notification_destination) -> Seed with a single row where id=1, enabled=0, destination='me'.

### Component C: Web Dashboard (Front-End & Interface)
* **Live Stream Feed:** Showcases captured comments, highlighted matched keywords, and user profiles.
* **Profile Deep-Linking Rules:** To ensure you can always message a user directly, apply fallback logic based on username availability:
    * *If username exists:* Render the profile handle linking to `https://t.me/username` (Targeting `_blank` to open in a new tab).
    * *If NO username exists:* Render a link displaying `[No Username - Click to Chat]` that uses the native deep link protocol targeting the numerical sender ID: `tg://user?id=sender_id`.
* **Management Console:** A dashboard view to add/delete monitored keywords and visualize currently tracked chats.
* **Security:** Implement basic HTTP Basic Authentication or token-based login to prevent unauthorized access over the public web.
* **Data Sanitization:** Strip or sanitize all HTML/Markdown markers from incoming raw message content before rendering them on the web view to entirely eliminate Cross-Site Scripting (XSS) risks.

### Component D: Telegram Notification & Dynamic Routing Feature
* **Web UI Dashboard Controls:** * Add a visible toggle switch to easily enable/disable Telegram notifications.
    * Add an input text field labeled "Notification Destination" allowing the user to enter a Telegram handle (e.g., `@my_worker`), a numerical user or group ID, or leave it as `'me'` (to route straight to your personal Saved Messages).
    * Changing either field must trigger an AJAX `POST` request to update the SQLite `settings` row instantly without requiring a page refresh.
* **Parser Dynamic Routing Loop:** * In the background worker script, immediately after a keyword hit is verified and saved to the DB, query the `settings` table.
    * If notifications are enabled, compile a clean, HTML-formatted text notification payload detailing the keyword matched, group name, user, and original comment.
    * Route the payload directly to the target stored in the `tg_notification_destination` configuration value.
    * Wrap the `send_message` action in a try/except block to catch routing exceptions (e.g., if the user enters an invalid username, or if that external account has blocked the UserBot session).
* **Unified Link Rules:** The profile link generated within the text of the sent Telegram notification must mirror the Web UI fallback rules exactly: use the HTML anchor format `<a href="https://t.me/username">@username</a>` if a handle is available, and fallback to `<a href="tg://user?id=sender_id">User Link</a>` if the user has no public handle.

## 4. Russian Geopolitical & Compliance Guidelines
* **Data Localization (Federal Law No. 152-FZ):** The application will run locally on Beget servers physically located inside the Russian Federation. Ensure no external, non-Russian cloud dependencies or tracking metrics are utilized.
* **Network Resilience (TSPU / Deep Packet Inspection Throttling):** Code defensively against packet loss, timeouts, and IP blocks. The connection manager must catch all network-layer errors (`ConnectionError`, `TimeoutError`) and cleanly attempt automated reconnection.
* **Proxy Adaptability:** Expose native configuration variables for MTProto or SOCKS5 proxies in the app's settings block so that traffic can be rerouted smoothly without rebuilding the code core if regional throttling spikes.
